# FarmaCheck — plano único de conclusão

**Plano ativo do Game Farma.** O escopo deste arquivo cobre somente melhorias e integração do game: gameplay, conteúdo, modelos, interface, acessibilidade, áudio, desempenho e QA do produto.

## 1. Entrada obrigatória para a próxima execução

1. Ler este plano, especialmente estado atual, sequência de entrega e critério de encerramento.
2. Conferir `git status --short` e somente os arquivos/evidências da tarefa escolhida. Preservar alterações existentes; não limpar o checkout compartilhado.
3. Selecionar uma entrega ainda aberta, registrar ID, resultado esperado, arquivos e validação necessária. Executar até produzir resultado verificável ou identificar uma dependência concreta.
4. Atualizar o estado no catálogo e o checkpoint ao fim da entrega. Continuar a próxima tarefa viável dentro do pedido vigente; uma subtarefa concluída não encerra o projeto.
5. Consultar histórico apenas para uma dúvida específica. Não reler milhares de linhas nem reconstruir todo o projeto em cada retomada.

**Autoridade documental:** instruções atuais do usuário → este plano para escopo/fila → código, manifests e evidências para comprovar estado. Divergência deve ser reconciliada; prosa antiga não sobrepõe o arquivo efetivamente usado. `resumo.md`, `task_plan.md`, `PLANO.md`, `MASTER_PLAN.md`, `planejamento.md` e roadmaps anteriores são registros de apoio, não filas concorrentes.

Entregar o FarmaCheck educacional web 3D estilizado, com os 14 pacientes, atendentes planejados, cenário O0–O8, atendimento PT/EN, acessibilidade, voz/ditado com fallback e progressão consistente. O fluxo deve funcionar com IA desligada; IA opcional não controla fatos ocultos nem pontuação.

Preservar Ana e balcão aprovados, identidades dos casos, Three.js/DOM/Vite e regras determinísticas. Finalizar o game inclui aparência, uso real, conteúdo clínico revisado e validação do funcionamento integrado; arquivo gerado ou teste isolado não basta.

## 6. Validação proporcional e evidência de conclusão

Para cada entrega registrar: **ID, mudança, arquivo/hash ou commit, comando/procedimento, ambiente, resultado, evidência, limitação e próxima ação**. Datas e nomes de versão não substituem hash quando o arquivo foi sobrescrito.

| Mudança | Verificação necessária |
|---|---|
| Somente documentação | Ler consistência/links/IDs; quando solicitado, `npm run test:docs-links`. Não rodar toda a QA do jogo por edição textual. |
| Lógica/UI/voz | Teste focal do contrato alterado e fluxo browser afetado; repetir integração ampla no fechamento do lote. |
| Personagem | Gate estrutural/topologia, A/B visual, Walk/Idle/contato e integração do caso; ledger e galeria no mesmo hash. |
| Cenário | Props/carga/fallback, POVs e contato; layout desktop/celular e fluxo afetado. |
| Integração do game | `npm run check`, testes de gameplay e conteúdo do game, build Vite de produção e QA browser dos fluxos/ativos afetados. Executar gates específicos do game em vez de um agregador que misture escopos. |

`qa:case-models` e `qa:avatar-cache` precisam de **Vite DEV**; o build estático não expõe sua instrumentação. `qa:all` já administra Vite para esses gates. Os demais gates que usam `QA_URL` precisam do app de QA correto disponível. Ler os argumentos do runner antes de executar.

**Cuidado com falso verde:** `qa:all` pode retornar sucesso pulando browser quando o servidor está ausente; também possui modos `--fast` e `--dev-only`. Conferir a lista de gates executados e os SKIPs, não apenas exit code. `qa:flow:matrix` usa chegada simulada; exige complemento do QA real de caminhada. Não somar reruns de snapshots diferentes como se fossem uma execução integral da versão final.

Preservar PASS válido quando a alteração não afeta seu contrato. Não repetir suites caras sem mudança, falha ou evidência faltante. Validar a integração do game e corrigir problemas reais sem reduzir os critérios de qualidade.
